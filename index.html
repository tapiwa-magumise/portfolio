Summary

My portfolio, drawn as AWS architecture: tapiwa-magumise.github.io/portfolio. Each area of my work is an account in an AWS Organization, and each project is drawn the way AWS reference diagrams are drawn, from that project's own Terraform, compose files and charts. Opening a project shows a console page built from its repository's README and docs.

Status

Live on GitHub Pages, published by CI after the browser tests pass. The move to CloudFront in front of a private S3 bucket waits on AWS account verification; the Terraform for that is in the first version's repository.

The problem it solves

A list of project cards says what someone built but not how the pieces fit, and a cloud engineer's work is mostly how the pieces fit. Here the visitor walks the architecture: each choice draws the next part of it, going back takes away the branch they left, and every part can be opened to see what it does in the project.

How it works
  1. data.js holds the whole drawing: the accounts, the projects, each project's detail with its boundaries, services and numbered flow, and each project's tags.
  2. scripts/build_console.py reads each project repository's README and decisions record and writes console-data.js, so the console pages say what the repositories say.
  3. app.js lays the tree out, draws it with a pen and moves the camera. console.js builds the console pages and search.js the search and tags.
  4. scripts/build_outline.mjs runs the same page builders under Node and writes a plain text version of everything into index.html. That is what visitors without JavaScript, screen readers and search engines read.
  5. CI checks the text version is current, runs the browser tests on a desktop and a phone profile, and only then publishes to GitHub Pages.

No framework and no build step: the files in the repository are the files that are served, about 1,000 lines of JavaScript.

Testing

17 browser tests in Playwright, run on a desktop and a phone profile. They cover drawing and retracting branches, opening console pages and links straight to them, choosing a part from its Resources row, search and tags, blueprint mode and the system dark setting, the skip link to the text version, screen reader announcements, no sideways scrolling, thumb-sized controls on a phone, reduced motion, and the whole site with JavaScript switched off. Any script error fails a test.

Summary

The foundation an organisation builds before it runs anything serious on AWS: separate accounts for separate jobs, guardrails nobody can switch off, one tamper-evident audit trail, central security monitoring, and single sign-on instead of passwords and access keys. Everything is Terraform, split into four stacks that are tested on every push without touching a real AWS account.

The problem it solves

Most companies start with one AWS account. Production, testing, experiments and billing all live together, everyone has broad access, and one mistake (a deleted log, a public bucket, a forgotten expensive instance) can affect everything. Auditors then ask who did what, and there is no reliable answer.

A landing zone fixes the structure before the workloads arrive:

NeedHow this landing zone meets it
Contain mistakes and breachesSeparate accounts per purpose; a problem in sandbox cannot reach production
Rules that cannot be bypassedService control policies apply to every account, including its administrators
Prove what happenedOne organisation-wide CloudTrail, in an account most people cannot touch, with Object Lock and signed digests
Spot threats and misconfigurationAccess Analyzer across the organisation; GuardDuty and Security Hub ready to switch on
No shared passwords or keysIAM Identity Center: people sign in once and get time-limited roles per account
Control spendA budget alert per account, and SCPs that block expensive services in sandbox
Structure
Root
├── Security          log-archive · security-tooling
├── Infrastructure    shared-services
├── Workloads
│   ├── Prod          workloads-prod
│   └── NonProd       workloads-nonprod
├── Sandbox           sandbox (cost-capped)
└── Suspended         accounts being closed (everything denied)

Testing

Nothing here needs a live organisation to test.

  • 19 Terraform unit tests (terraform test) run each stack against a mocked AWS provider. They check, for example, that every account lands in the right OU, the region guardrail is attached at the root, accounts are never auto-closed, paid security services stay off unless enabled, and developers cannot change production. They also check that invalid input is rejected.
  • IAM Access Analyzer validates every SCP against AWS's own policy grammar. CI uses a role that can call nothing except access-analyzer:ValidatePolicy.
  • Checkov scans every stack. Deliberate exceptions are listed with reasons in .checkov.yml.

Summary

Deploys are paused. Since 18 October 2026 AWS has refused Lambda calls on this account, so the plan step fails; tests, format, validate and Checkov still pass. I'm currently working on it with AWS.

Branches upload a weekly sales CSV. Within seconds every row is checked, good rows land in a queryable data lake, bad rows are kept with the reason they failed, and every file gets an audit record. Failures alert someone by email. The whole stack is Terraform, deployed by GitHub Actions with no stored AWS keys, and it is designed to run at zero cost.

The problem it solves

A retailer's branches each send a sales spreadsheet. Head office combines them by hand, errors surface only after reports have gone out, and nobody can say which file a number came from. This pipeline replaces the manual step with one that:

  • Validates every row against explicit rules (date, branch, SKU format, units, revenue, cost, duplicates).
  • Never silently drops data. Rejected rows are stored with every reason they failed, so the branch can fix and resend.
  • Records an audit trail per file: status, rows loaded, rows rejected, start and finish time.
  • Is safe to re-run. Uploading the same file twice does not double-count sales.
  • Tells a person when something breaks rather than failing quietly.

Summary

A backend for small businesses to invoice customers and record payments, built the way payment systems have to be: a retried request never charges twice, two payments at once cannot overpay an invoice, every movement of money is a balanced ledger entry, and every event reaches the merchant's systems as a signed webhook, even if a server crashes at the wrong moment.

Python, FastAPI, PostgreSQL, Redis, with a React and TypeScript dashboard, OpenTelemetry tracing, Prometheus metrics and Grafana dashboards.

How a payment works
  1. The client sends POST /invoices/{id}/payments with an Idempotency-Key.
  2. The API locks the invoice row, so concurrent payments for it queue rather than race.
  3. If that key was already used with the same request, the original payment is returned with Idempotent-Replayed: true. With a different request, 409 Conflict.
  4. Otherwise it checks currency, status and outstanding balance, then in one transaction records the payment, two ledger entries, the invoice update and the webhook deliveries.
  5. A worker sends due webhooks every five seconds, signed with HMAC-SHA256, retrying with backoff.

Summary

Two microservices that take and fulfil orders through events, built to keep working when parts of the system fail. An order is never lost, even with the event broker or the inventory service down; stock is never oversold under concurrent load; and every event takes effect exactly once, in order.

  • Orders service: TypeScript, NestJS, PostgreSQL
  • Inventory service: Java 21, Spring Boot, PostgreSQL
  • Between them: Apache Kafka for events, gRPC for queries
  • Platform: Kubernetes (kind) with Helm, OpenTelemetry tracing to Jaeger, CI on GitHub Actions
How an order flows
  1. POST /orders with an Idempotency-Key. Orders asks inventory over gRPC whether the stock exists (300 ms deadline, advisory).
  2. In one transaction, orders saves the order as PENDING and an OrderPlaced event in its outbox, then replies 202 Accepted.
  3. A relay publishes the event to Kafka, keyed by order id.
  4. Inventory consumes it and, in one transaction, records the event id, locks the products, reserves the stock and writes StockReserved (or StockRejected with the reason) to its own outbox.
  5. Orders consumes the result and moves the order to CONFIRMED or REJECTED.

Summary

An assistant that answers questions about UK public procurement from 260 published documents: the Procurement Act 2023 guidance, the current procurement policy notes, and a month of tender notices from Find a Tender. Every answer cites its passages, every model call runs in London, and personal data in the notices is masked before anything is stored.

Status

Built and tested, with the evaluation waiting on Bedrock access. On 18 October 2026 every on-demand Bedrock quota in the account dropped to zero, so no model can be called until AWS restores them (see the build log). The evaluation results will go in docs/03-results.md, and the similarity threshold will be set from them.

How an answer is made
  1. Regular expressions mask email addresses and phone numbers in the question.
  2. The input guardrail blocks prompt attacks and two denied topics (legal advice on a specific case, and collusion), and masks names.
  3. The question is embedded and searched two ways, by meaning and by wording, and the results are fused by rank. Six passages are kept.
  4. If even the closest passage is a weak match, the assistant says the documents don't answer the question. No model is called.
  5. Nova Lite answers from the six passages only, citing them, at temperature 0.
  6. The output guardrail checks the answer against the passages. An answer below 0.75 for grounding or 0.5 for relevance, or with no citation, is withheld.
  7. The masked question, the outcome, the passage ids, the scores and the cost go into the audit log.
